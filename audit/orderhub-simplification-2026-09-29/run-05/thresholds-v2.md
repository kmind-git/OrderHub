# OrderHub 验收阈值 v2：本地闭环与启用前指标

日期：2026-09-29。范围：本地 `x86_64-pc-windows-msvc`，使用仓库锁定的 stable Rust。
本版由用户要求“数据库仅保留并无 C 化、功能以后验证，评估过严门槛”触发。
它调整 v1 指标的适用阶段和功能数据集，不修改历史测试结果，也不表示当前代码达到指标。
主方案的现行阈值引用本文件；[v1](../../orderhub-simplification-2026-09-27/run-01/thresholds-v1.md)
作为历史及后续容量目标保留。

## 1. 本期保留的边界

| 项目 | 工程默认值或不变量 | 本期验证 |
| --- | --- | --- |
| 行情新鲜度 | 报价最多 2 秒，交易状态最多 5 秒 | 使用可控时钟验证边界和恢复；缺失、断连、序列缺口或未知状态关闭新增风险 |
| 账户/持仓新鲜度 | 最多 10 秒 | 验证版本化快照/心跳、过期和重新同步；受控撤单仍校验归属 |
| 时钟偏差 | 最多 500 毫秒 | 对可信来源比较；未来时间或超差不放行，不用真实等待扩大测试时长 |
| 核心队列 | 最多 4,096，至少 1,024 保留给撤单/对账 | 定向饱和测试验证拒绝与预留，不要求先跑十分钟全链路负载 |
| 执行事件队列 | 最多 4,096 | 溢出可观察并停新增风险，不能丢事件后继续交易 |
| 日志写队列 | 最多 1,024 | 有限等待、显式失败、持久化确认前不发单 |
| 订阅与回放 | 每流 256 条、每节点 128 流、每页 1,000 条 | 定向边界、慢消费者断开与游标补流测试 |
| 进程崩溃 RPO | 已确认本地日志提交丢失数为 0 | 提交/响应/发送边界故障与真实进程重启，核对稳定 ID、额度和事件 |
| 本地备份恢复 | 一致性、schema、epoch、ID、防重索引正确 | 至少一次备份/恢复往返；未知交易所事实保持 HALTED |

以上新鲜度与队列数值是当前工程默认值，不代表生产容量承诺。适配源心跳或业务配置变化时，
先写明约束和新版本，再运行相关边界测试；不能为了让现有失败通过临时放宽阈值。
故障时准确阻断新风险、精确金额计算、幂等、权限和持久化语义不因规模较小而减弱。

## 2. 本地功能与恢复数据集

- 普通功能回归参考数据：2 个提交方、2 个账户、2 个合约、100 个订单意图；
  覆盖提交、撤单、部分成交、拒单、重复回报、乱序及跨提交方访问，保存预期账本结果。
- 日志/检查点回放参考数据：1,000 条确定记录，包含未决、终态与检查点后的尾部记录。
  固定种子、schema、稳定 ID、价格/数量/费用和预期摘要；记录实际条数与字节数。
- 每个崩溃或数值边界用能触发该分支的最小样本，不能为了凑规模反复执行相同断言。
  队列/分页等边界超过普通 fixture 大小时，单独构造对应数量；不受上述参考数量限制。
- 磁盘错误先在持久化抽象注入同类 I/O 错误，证明错误传递、拒绝受理与恢复行为，
  再保留最小真实进程重启测试。需要验证 OS 特有行为时才增加隔离故障环境。
- 记录端到端耗时、RSS、峰值磁盘和恢复耗时；本期以结果正确、资源有界为门槛，
  不用该数据集宣称通过下节的吞吐、p99 或大数据恢复指标。

这是功能验收的初始数据配额，不能替代具体场景的预期结果设计；
不存在真实旧数据时使用受控旧格式样本并记录数据清点依据。

## 3. 后置目标与触发条件

| v1 项目 | 原目标（保留） | 何时执行 |
| --- | --- | --- |
| DB 投影积压 | 10,000 条、64 MiB、最老 30 秒，先到者触发门禁 | DB 启用前实现并验证；关闭时不创建积压、不影响 READY |
| 介质丢失备份 RPO | 最多 15 分钟 | 准备实际持续运行/部署并承诺该服务指标前，验证备份周期与完整恢复 |
| 恢复 RTO | 参考环境最多 30 分钟到 READY | 所需外部对账证据具备并准备承诺自动恢复时，按完整过程测量 |
| 容量数据集 | 10 提交方、100 合约、约 10,000 活跃订单 | 声明容量或提高实际负载前 |
| 持续流量 | 每秒提交/撤单各 1,000，持续 10 分钟，各 600,000 次 | 同上；记录成功、拒绝和失败，不能用 journal 单项吞吐代替 |
| 大规模恢复 | 至少 1,200,000 命令记录与 10,000 活跃订单 | 验证该级别数据量的恢复能力前 |
| 延迟与内存 | 端到端提交/撤单 p99 ≤ 250 ms，峰值 RSS ≤ 2 GiB | 在完整容量数据集下测量，不能套用空载或小型 fixture 结果 |

这些工作由后续 DB 启用、自动恢复或容量/部署任务承接。触发前状态为“延期、未验证”，
不阻塞本期 P1 或本地 MVP；触发后失败/缺失必须阻止相应能力启用或指标声明。
若拟承诺规模改变，应先评估并发布新阈值版本，而非默认将 v1 当作已知业务需求。
