# OrderHub 精简方案调整与测试门槛评估

日期：2026-09-29。类型：方案修订，不是实现或测试通过报告。

依据用户本次决定，PostgreSQL/Redis 现阶段仅保留并完成无 C 化，真实服务验证延期。
同步修订[主方案](../../../orderhub-project-simplification.md)、
[无 C 子方案](../../../orderhub-tls-stack-removal.md)和[阈值 v2](thresholds-v2.md)。
2026-09-27/28 的 audit 报告按原范围保留，不覆盖历史证据或追溯勾选验收。

## 1. 评估结论和调整

原方案把技术可行性、最终集成、可选能力和容量承诺放进了过于串行的阶段门槛。
问题集中在验证时点与范围；订单正确性、精确风控、持久化、权限与不确定恢复的约束继续保留。

| 原要求/现象 | 对当前落地的影响 | 本次调整与保留条件 |
| --- | --- | --- |
| P1/C2 要求真实 DB 认证、事务、连接池和重连 | 未使用的服务阻塞整体项目；本机服务缺失被放大成全阶段阻塞 | DB 本期仅无 C 化，A07–A08 延到启用前，保留 schema/API/TLS/测试材料 |
| P1 只写原型退出，C2 却写实际应用集成，C6 又包含最终矩阵 | 阶段边界矛盾，容易把 P8 搬到 P1 | 分列 P1 技术退出、P3–P7 集成、P8 最终无 C、能力启用前行为验收 |
| P2 必须等待整个 P1；P7 必须等待整个 P6 | 契约设计和独立消费者迁移被无关项目阻塞 | 依具体接口/消费者推进；各阶段仍分别记录通过和未完成，不跳过真实依赖 |
| C4/C5 先完整替代研究框架的压缩、生成、模糊测试路径 | 为将删除的能力重复建设替代实现 | 先确认消费者与旧数据，仅验证必要保留技术；退役路径完成迁移/删除核对 |
| 每个配置在每阶段做干净 debug/release 和完整行为测试 | 重复验证同一 provider，产生大量磁盘产物 | P1 关键路径一次干净验证，日常增量；P8 各 cfg 实际链接，release 至少 B/G/U 和独立分支 |
| 多个适配器重复底层证书/算法的全套组合 | 相同断言重复，而配置错误仍可能漏检 | 底层共用完整已选矩阵，消费者测试配置传递、错名拒绝、错误处理与禁止降级 |
| 要求借到不支持 Graviola 的 CPU，覆盖所有 TLS 可选模式 | 单机项目被未承诺的硬件/模式卡住 | 本机真实运行，缺失指令门禁注入；新 CPU、mTLS、系统根或代理在实际启用前验证 |
| 密码安全评估没有明确产物或结束条件 | 容易无限等待“生产级证明” | 对锁定候选做有结论的公告/维护/算法/平台评估；适用的严重问题仍阻塞，不要求自建密码审计项目 |
| 默认 120 万记录恢复、十分钟 2,000 次/秒流量及 p99/RTO 门槛 | 在功能尚未闭环时先承担容量认证 | v2 使用小型确定数据验证正确性，v1 容量与部署目标在对应承诺前执行 |
| 每个磁盘错误都依赖真实填满磁盘 | 操作成本高，且本机已出现编译耗尽磁盘 | 确定性 I/O 故障注入加最小进程崩溃/重启；OS 特有问题才安排隔离实机验证 |
| 自动对账依赖外部模拟交易所新增查询接口 | 外部项目阻塞已有订单联调与代码清理 | 本期仍要求真实模拟交易所订单/撤单/成交/重连；查询不足时保持 HALTED，自动恢复单独启用 |
| 备份/格式迁移默认针对所有可能旧数据 | 容易形成没有实际数据对象的迁移工程 | 以 P0 数据清单为依据；有数据就副本演练，无数据记录依据并用旧格式 fixture |

“没有外部审计报告”与“已知严重问题未解决”是不同结论。前者要求记录风险和本地采用边界，
后者必须处理；本次调整没有批准任何新密码后端，也没有撤销已有证书校验要求。

## 2. 数据库本期仍须完成的工作

1. 保留现有生产 crate/API、schema、SQLx 本地补丁、Redis TLS 和必要工具/测试来源。
2. 将无 C provider/feature 真实接入保留代码；R/P/PT 各实际构建/链接，U 验功能并集。
   只让独立原型通过或仅 cargo check 都不能视为数据库无 C 化完成。
3. 对改动路径运行无需真实服务的本地 TLS/配置测试，审查依赖、build.rs、链接及动态加载入口。
   底层测试可以复用，必须保留错误主机名、证书不可信/过期和禁止自动降级的覆盖。
4. DB 默认关闭且无投影积压；正常入口拒绝未验收的启用配置。隔离验证入口可显式选择测试服务。
5. 以“保留、可构建、功能待验证”描述能力；真实认证、事务、池化/重连、消息、迁移和 A08
   由后续启用任务完成，届时测试未通过不得开放对应配置。

本期不要求安装数据库或容器，也不要求实现尚未使用的双后端 outbox/投影产品功能。
已有后端方法与测试保留；新增功能和未实现错误分支列入启用清单，不能悄然丢弃。

## 3. 不宜删去或后置的检查

- 受理前持久化确认、提交结果未知时保留占用、禁止换 ID 盲重发、已确认提交崩溃 RPO 为零。
- 幂等、重复/乱序回报、撤单竞争、精确金额/费用、额度结转及恢复后一致性。
- 身份绑定、跨提交方权限、输入解析不 panic、队列有界和撤单保留通道。
- 行情/账户陈旧门禁、缺失交易所事实不进入 READY、恢复时防重及 epoch/单实例保护。
- 启用 TLS 时的主机名/证书校验与禁止降级；必要保留路径的真实无 C 构建/链接证据。
- 消费者迁移后再删除模块，有必需旧数据时保护数据并验证迁移。

这些检查可用小数据集和针对性的故障用例完成，不要求以容量压测替代功能验证。
真实模拟交易所未运行时只能标记内部链路完成，不能声称本地端到端 MVP 已验收。

1. 完成 C0 消费者/必要数据范围与残留项分派；将确定退役路径移交 P3/P7。
2. 给锁定 TLS 候选形成有结论的本机适用性与安全/维护评估，补实际缺少的门禁测试。
3. 检查已有 SQLx/Redis/gRPC/HTTPS 原型的来源、补丁可复现性和构建/链接证据缺口；
   源码或构建输入未变时复用已保存记录，发现缺口再执行定向验证。
4. 必须保留且技术仍不确定的密码/压缩/生成路径补小型原型；完成生产接入清单。

P2 的本地事务/恢复契约可以开始；涉及未定密码后端的最终选型仍等待相应 P1 结论。
先以 P6 提供受限且明确能力范围的本地 MVP，再以 P8 完成全保留代码的精简与无 C 验收。
