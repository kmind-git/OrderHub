# 本地存储与提交契约

状态：P5 本地 profile 事务/投影已实现并验收；P6 检查点、迁移和恢复仍待实施。证据见 [业务运行时](business-runtime.md)。主方案见
[项目精简方案](../../orderhub-project-simplification.md)。本契约只规定 OrderHub
本地业务账本；保留的 PostgreSQL/Redis 客户端现阶段只作无 C 化，未启用外部投影。

## 权威数据与格式

OrderHub 使用一个专属 redb 业务库作为请求、订单、成交、归属、额度及对外事件的
本地权威记录。交易所回报和覆盖完整的查询是外部执行事实；本地库不能证明一笔
已进入发送边界的订单没有到达交易所。Nautilus Cache/Portfolio 是可重建的
执行视图，原有 `event_store` 可提供诊断材料，但不与业务库构成原子双写，
也不作为准入 ACK 的权威来源。

首个持久格式版本定为 `schema_version = 1`，使用 redb 表和 UTF-8 JSON 的
**有版本 envelope**。每条记录至少保存 `schema_version`、`journal_epoch`、
`journal_seq`、`kind`、业务 payload、稳定请求/订单/成交身份和时间来源。
金额、价格、数量、费用均保存十进制字符串及币种/精度上下文；不将 JSON
浮点数写入账本。每个版本有显式解码器和迁移规则；未知版本阻止 READY，
不靠 serde 默认值填补缺失的经济字段。校验摘要针对 envelope 内**实际存储的 UTF-8 payload 字节**计算，
不用重新序列化后的字段顺序判断数据相等。

| redb 逻辑表                       | 内容与约束                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| `META`                            | schema、日志代、最后提交序号、检查点/投影水位、实例标识；同库事务更新。                     |
| `JOURNAL`                         | 单调序号键的完整业务事实；保留受理、发送边界、回报、恢复和状态转换。                        |
| `REQUEST_INDEX`                   | `(epoch, submitter, rpc_method, request_id)` 到原请求结果/订单 ID；归档事件时不删除防重键。 |
| `ORDER_INDEX` / `EXECUTION_INDEX` | 客户单、券商单、稳定成交 ID、修正/撤销关联与归属；重复回报不重复产生经济效果。              |
| `RESERVATIONS`                    | 暂占恢复依据、正式预占、剩余量、费用缓冲、规则版本及账户/策略归属。                         |
| `PROJECTION`                      | 与业务事务同库提交的授权查询状态及已提交高水位；内存快照只从该版本发布。                    |
| `CHECKPOINT`                      | 完整恢复材料的不可变版本化 blob、摘要、日志水位及清单；至少保留最近可验证的一组及其日志尾。 |
| `DB_OUTBOX` / `DB_WATERMARK`      | 仅保留 schema/接口位置；后端关闭时不生成待投递行，也不因关闭的服务阻断 READY。              |

P5 已实现 JOURNAL/REQUEST_INDEX/META、订单/原结果/成交索引、账户与策略余额、
输入/控制状态及每条事件的不可变投影。订单同时保存发送意图和剩余预占。
检查点和旧经济数据迁移在 P6；DB outbox 在后端启用前实现。无版本旧库和
未知版本被拒绝，不作为空库打开。

## 一次业务提交

核心线程串行完成校验与**暂占**，把事务交给有界持久化工作线程。同一 redb
写事务内至少提交请求结果、订单意图、正式预占、待发送记录、相关索引、
规范化对外事件及投影版本。批量提交可包含多笔互相独立的请求，但每笔在
批次内仍按准入顺序核算额度；批次 durable commit 成功后才逐笔 ACK。
结果回报事务同样原子提交稳定成交 ID、累计数量、价格、费用/币种、账户
和策略归属、额度结转、订单状态及对外事件。内部记录可占日志序号；
对外事件使用自身稳定 `event_id` 和顺序，不能把时间戳当成日志游标。

| 工作线程结果                      | 核心线程与客户端动作                                                                                 |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 明确成功，能读回提交序号          | 暂占转为正式预占，发布同版本投影；受理可返回 `ADMITTED`。                                            |
| 明确未写入，且可证明没有派发      | 回滚暂占，返回不可用/写入失败并关闭相应准入；不能虚构持久的业务拒绝，不得先发单。                    |
| 结果未知，例如提交后连接/进程故障 | 保留保守占用，关闭新单门禁；按请求键/提交水位读回或恢复，查明前不能视为失败、释放额度或另造订单 ID。 |

`DISPATCH_STARTED` 必须先持久提交再调用执行通道；它表示**可能已发送**，
不是交易所确认。网络错误或 RPC deadline 也不能反推本地事务失败。
写入错误必须从 `worker`/`exec_wiring` 传到业务门禁；不能吞掉错误后继续
发布 READY、释放额度或推进 WatchEvents 游标。

## 投影、检查点和备份

GetState、RequestLookup 和 WatchEvents 只观察已提交的 `PROJECTION` 与
`JOURNAL`。一次业务事务中记录与投影的水位必须相同；内存快照只能在提交
确认后发布，进程重启由持久数据重建。分页固定同一个水位 N；补流扫描 N
之后已提交事件，内存消息只负责唤醒。日志回收同时保护未过期快照租约、
完整恢复检查点的尾部以及未来已启用 DB outbox 的未消费行。

检查点在暂停派发/排空回报后的确定切面 N 制作，覆盖请求防重索引、订单、
成交、账户与策略归属、额度、合约/ID 映射、投影、schema、epoch 以及引擎
重建材料。将不可变 blob、内容摘要及清单写入 redb 并 durable commit 后，
才允许回收旧尾部；半写或未引用 blob 不能参与恢复。若另存外部 blob，
必须先完成刷盘、摘要验证和原子清单发布，不能仅凭文件名或时间戳配对。
原 `event_store` 水位可作交叉核对，不能替代业务检查点版本。

备份使用一致的 redb 读视图或暂停写者后的受控副本，带 manifest、schema、
epoch、最后完整序号、内容摘要和配置/二进制标识；P6 使用 BLAKE3，源码审计使用 SHA-256。
不可直接复制仍在
写入的文件并宣称一致。恢复后验证清单、blob 和连续日志尾，旧备份须换
新 epoch 并重新对账，未取得交易所事实前保持 HALTED。已确认本地提交在
进程崩溃后丢失数应为零；介质损毁的 RPO/RTO 按
[阈值 v2](../../audit/orderhub-simplification-2026-09-29/run-05/thresholds-v2.md)
的启用阶段另行认证。

P6 已实现一致逻辑 blob、唯一文件名、同步发布的 manifest、原子恢复增量及换代恢复栅栏。
实现、离线命令、旧材料迁移边界和完整历史回退见 [恢复运行时](recovery-runtime.md)，
实测数据及故障证据见 [P6 记录](../../audit/orderhub-simplification-2026-10-02/run-16/P6-acceptance.md)。
本期不回收恢复链或防重索引；缺少经济字段或原生事件的旧库须明确补充来源，不能自动猜测。

## 数据库接口预留

未来启用外部投影时，每条要投递的业务事实与本地事务同提交 `DB_OUTBOX`，
外部消费者以 `(epoch, journal_seq, event_id)` 幂等写入，并在本地持久记录
消费水位。不得把 redb 和 PostgreSQL/Redis 宣称为原子双写。启用配置
必须先验证 schema、TLS、认证、错误/重试、积压上限和交易必需/可选策略；
本期关闭后端时不得启动投影循环或积累 outbox。缺失方法应由配置门禁拒绝，
不能让可达业务路径落入 `todo!()`。
