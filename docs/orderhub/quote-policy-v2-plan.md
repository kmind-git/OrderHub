# OrderHub 价格保护与报价新鲜度门禁移除方案

制定日期：2026-10-11。状态：S1–S3 已实施，并通过 Windows x64 本地验收。
目标仓库：`D:/projects/zcodeworkspace/nautilus_trader`。
本方案作为 P8 验收后的新增业务规则变更，原 P0–P8 记录保留原日期与证据范围。

## 1. 变更目标

按用户要求移除两个功能：

1. 取消以卖价为参考、偏离超过 ±10% 时拒单的价格保护。
2. 取消因报价超过 2 秒、报价断流或报价序号缺口而阻断新增订单的规则。

订单继续使用客户端提交的限价，成交仍依据执行通道回报。
报价继续供持仓估值、浮动盈亏和账户/策略风险敞口计算。

本方案中的“新鲜度检查”限定为报价流。账户、交易状态及执行连接的原有规则继续生效。
本次实施已完成；新规则、命令、源码/产物摘要及边界见[补充验收](quote-policy-v2-acceptance.md)。既有阶段记录保持原证据范围。

它不是多档盘口增量。因此序号跳跃后，可使用合法的完整顶层替换，无须重建缺失档位。

## 3. 新业务规则

### 3.1 价格保护

- 删除运行路径中的 `PRICE_BAND` 拒绝分支。
- 删除 `price_band_fraction` 字段、固定 10% 值及相关上下界验证。
- 不增加开关或新的默认价格带，不把阈值扩大到其他数值。
- 保留正价格、精确数值、合约 tick/精度、数量、单笔名义额、现金、持仓和风险敞口限制。
- 偏离参考价超过 10% 的订单，在其余条件通过时可以受理和进入执行链。
  如果该订单同时超出现金或单笔限额，仍按对应规则拒绝。

### 3.2 报价可用性与估值

采用最后一条合法且匹配当前合约定义的报价：

- 报价不设置最大年龄，不因运行时钟推进而使报价失效。
- 仅报价停止更新、报价连接丢失或报价序号出现缺口，不关闭新增订单门禁。
- 合法的新报价继续更新 Cache 和 Portfolio，敞口检查继续使用该报价的卖价作为参考。
- 报价停更期间沿用最后合法报价，并保留其真实时间戳、序号及来源；不制造新报价或心跳。
- 启动时仍需要至少一条合法报价；合约定义变更后需要匹配新定义的报价。
  这是估值所需数据的存在和匹配条件，不设任何报价年龄阈值。
- 旧报价可能使估值和敞口计算偏离当前市场；取消阻断后，这一影响属于新规则的业务边界。

### 3.3 报价接收规则

将报价的数据检查与交易准入分开：

1. 保留来源、合约修订、数值精度、正价格、整股数量、完整性及买价不高于卖价的检查。
2. 报价继续检查时间字段合法性，如源时间不能晚于接收时间、接收时间不能晚于当前时间。
   报价移除 2 秒年龄上限及 500 ms 源到接收延迟上限，避免隐藏的时效阻断。
3. 同一输入代内重复、旧序号或时间倒退的报价丢弃，不覆盖最后合法报价。
4. 较高序号的合法完整顶层报价可跨过序号缺口更新，不要求先收到额外的快照消息。
5. 无效报价丢弃并记录原因；已有合法报价时继续使用原报价。
6. 报价重连时允许用新的输入代及完整顶层快照建立新序号基线；只重置报价流状态，
   不因报价重连重置账户或交易状态。旧输入代的排队报价不得覆盖新报价。

报价的年龄、停止更新和序号异常可通过已有时间/序号信息及有界日志观测。
本次不新增行情 RPC、监控平台或另一套新鲜度判定阈值。

### 3.4 共享输入通道的边界

当前 JSONL 输入通道承载合约、报价、交易状态和账户四类事件。
实施时按已识别的事件类型区分故障归属，采用最小的内部状态/方法调整：

- 已识别的报价帧丢失、无效、序号异常，只更新报价观测；不调用全流失效路径。
- 账户或交易状态的丢失、异常，继续按原规则关闭相关新单门禁。
- 整条 JSONL 输入 EOF、无法识别类型的损坏帧、整个输入源断开，意味着其他必需输入
  也失去连续性，仍触发它们的原有门禁；不能将整体故障归为仅报价故障。
- 输入、定时、持久化和执行队列的资源上限保留；存储故障或执行连接丢失继续阻断新单。
- 不新建独立行情服务或增加线程，仅为明确报价故障归属增加必要的内部控制表达。

验收“报价断流不阻断”时，必须持续提供有效账户与交易状态，并保持执行连接有效。
整条输入源断开后仍阻断新单，是其他保留规则的结果，应记录实际阻断原因。

## 4. 行为对照与验收判据

下表的报价场景均以账户、交易状态、合约、执行连接、权限及额度符合要求为前提。

| 场景                                  | 新行为                                                |
| ------------------------------------- | ----------------------------------------------------- |
| 订单价格偏离卖价超过 ±10%             | 不产生 `PRICE_BAND` 拒绝；限价原值进入受理和执行链    |
| 报价年龄超过 2 秒，含长时间没有新报价 | 沿用最后合法报价，允许新单；不出现报价年龄上限        |
| 仅报价断流，其他必需输入继续有效      | writable 保持可用；允许受理和发送，撤单及回报继续处理 |
| 合法完整顶层报价序号从 10 跳到 13     | 接受更新，记录缺口；不关闭新单门禁                    |
| 重复、旧序号或非法报价                | 不覆盖最后合法报价；已有合法报价时不因该帧阻断        |
| 尚无任何合法报价或当前合约无匹配报价  | 不具备估值输入，拒绝新增订单，明确返回缺失原因        |
| 账户超过 10 秒、交易状态超过 5 秒     | 继续阻断新增风险；阈值保持原值                        |
| 停牌、非授权时段、账户归属/资金不足   | 继续按对应规则拒绝                                    |
| FIX 断连、持久化失败、恢复材料不足    | 继续关闭新单门禁并保留订单事实与占用                  |
| 同键重试旧 `PRICE_BAND` 拒绝请求      | 返回原持久结果；使用新的请求 ID 才按新规则判断        |

`GetState.writable/stale` 表示交易可写性和必需输入可用性，不承诺报价是实时行情。
报价异常不能单独产生 HALTED、INPUTS_UNAVAILABLE 或新的不可写状态。
发送前复核继续检查账户、交易状态、合约、截止时间和生命周期，不复核报价年龄/连续性。

## 5. 实施步骤

### S1：移除价格带并登记规则版本

- 修改 `journal.rs`、`ledger.rs`、`inputs.rs` 及所有 `RiskContext` 构造点。
- 新受理订单使用 `local-usd-v2` 风控规则标识；节点配置摘要包含本次策略版本。
- 在保留其他限额的情况下验证买卖单越过原上下价格带仍可受理。
- 原历史日志中的 `PRICE_BAND` 原因、请求结果和旧规则标识继续可读，不批量改写历史。

### S2：分离报价观测与准入检查

- 顺序处理 `apply`、`expire`、`check_ready`、`risk_context` 及报价故障归属。
- 移除报价年龄和延迟上限，保留最后合法报价和序号/输入代的防覆盖规则。
- 核对 `bridge` 受理、落盘后发送及 `commit_health`，确保三处采用相同新规则。
- 核对 gRPC `writable/stale`、启动就绪与恢复路径，避免隐藏的报价阻断。
- 保留核心线程独占 Cache/Portfolio，网络和磁盘继续经有界队列交给工作线程。

### S3：同步契约并完成局部验收

- 更新输入、风控、业务、恢复、状态/事件契约及主方案的当前业务规则说明。
- 原 P4/P5/P8 验收记录作为历史证据保留，另写本次变更的命令、结果、源码摘要和限制。
- 新记录明确旧 A01 报价时效/缺口阻断、A05 价格带、A13–A14 可写状态的预期已改变；
  原阶段结果不能直接证明本次新规则已通过。
- 按第 6 节执行受影响测试，全部必需项通过后标记本次变更完成。
