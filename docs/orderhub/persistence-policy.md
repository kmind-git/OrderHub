# 持久化策略：性能优先

2026-10-12：项目维护者接受成功受理和发送先于持久化完成，以性能优先。
本策略替代旧方案中“所有受理 ACK 必须等待 durable commit”的统一要求。
历史 P0–P8 验收记录保留当时语义，不作为异步模式零丢失的证明。

## 运行模式

节点配置 `ORDERHUB_PERSISTENCE=async|sync`，默认 `async`；其他值启动失败。
离线恢复工具和 `BusinessJournal::open` 默认使用 `sync`。

| 行为                | `async`，节点默认                                | `sync`                       |
| ------------------- | ------------------------------------------------ | ---------------------------- |
| 业务事务            | redb `Durability::None`，先在当前进程可见        | redb `Durability::Immediate` |
| 成功受理 ACK 和执行 | 进程内事务提交后可以返回、派发                   | 等待持久提交成功             |
| 查询、幂等、事件    | 读取进程内已提交版本，可能超过刷盘水位           | 读取持久提交版本             |
| 刷盘                | 独立线程每约 5 ms 检查，统一提升已提交前缀       | 每次业务提交                 |
| 崩溃恢复            | 只认可实际恢复出的完整持久前缀，ACK 尾部可能丢失 | 保留既有同步提交语义         |

启动时同步保存新日志代、订阅签名密钥和活动会话标记，然后才处理业务。
启动与停止阶段的同步写入是低频操作，不改变业务热路径策略。
异步启用后数据库元数据 schema 升为 2，业务 envelope 保持 1，恢复格式保持 2。
当前程序接受旧数据库 schema 1；只认识数据库 schema 1 的旧程序会拒绝异步库，
避免旧程序忽略活动会话/对账栅栏后误开放交易。切回 sync 不降低数据库版本。

## 当前实现的性能边界

事务仍原子更新请求键、原结果、订单、占用、成交、非报价输入、事件和恢复增量。
`async` 不等待该事务的磁盘同步；既有工作线程在进程内提交后回复，取消 600 μs 的
固定合批等待。每约 5 ms，后台线程提交一个 Immediate 事务，刷盘所有此前已提交事务。
没有新业务时不周期性生成无用的刷盘事务。

redb 同一库仅允许一个写事务。后台刷盘期间，新写事务仍可能等待同一写锁；
当前实现不是完全无阻塞的磁盘镜像系统。5 ms 是调度周期，不是丢失窗口或刷盘延迟上限；
磁盘、调度和系统负载可能延长实际持久化时间。

`GetState.persistence_mode` 返回实际模式；`durable_cursor` 返回后台已经确认刷盘的全局
前缀水位。`state_cursor` 是查询版本，不承诺已刷盘。分页快照固定版本不变，刷盘水位
独立变化。事件、成功 ACK 和同进程幂等结果可以先于刷盘确认。

## 报价仅保留内存

2026-10-12：维护者要求行情不用落盘。有效报价仍在核心线程更新 Cache/Portfolio，
用于估值和敞口，但不生成业务事务、输入投影、事件记录或恢复增量，也不推进业务游标。
此规则同时适用于 async 和 sync；仅有报价变化不会触发后台刷盘。
日志入口拒绝含报价的整批写入，避免直接调用绕过输入运行时的策略。

GetState 快照和 WatchEvents 不返回报价。报价没有持久回放能力；重启后不恢复报价，
启动及合约修订后的第一条合法匹配报价必须来自当前行情源。
合约定义、交易状态、账户、订单、成交、费用及占用继续按所选模式保存。
订单限价和成交价格是经济事实，继续持久化；报价的内存估值功能保留。

旧数据库中的历史报价不改写，恢复链校验和完整备份仍保留原历史；Cache 恢复和对外
查询/事件流跳过这些报价。新接收的报价不进入日志、投影、恢复增量或新增检查点材料。
业务 envelope schema 1 与恢复格式 2 不变；节点配置摘要标记报价仅保留内存的策略。

## 故障与恢复

后台写入/刷盘失败会记录故障，核心健康轮询关闭新风险门禁，后续写入拒绝；
已经返回的成功结果不会被追溯改写为拒单。未解决的资金和持仓占用继续保留。

进程或主机故障可能丢失已经 ACK、甚至已经发往执行端的尾部，包含原请求结果、
订单、回报、占用和事件。未恢复出的请求不能据此证明交易所没有订单；
缺少 `DISPATCH_STARTED` 也不能证明没有发送。对账前不能盲目创建替代订单。

每次异步启动同步切换新 epoch，并保留已有客户订单 ID 和经济事实。
旧 epoch 的变更请求和订阅 token 失效；使用新 epoch 查询已经恢复出的原订单。
这避免尚未刷盘的尾部丢失后复用原订单 ID。

正常 Ctrl+C：关闭新风险、排空本地回报、提交 STOPPED、等待刷盘、同步清除活动会话标记，
再发布检查点。直接 drop 对象会尝试刷盘，但不等同于完成节点正常停机。
异常结束留下会话标记：下次启动保持 HALTED，持久保存对账栅栏；即使库里没有业务订单，
也不据此证明不存在执行端订单。随后一次正常停机不会自动清除这个对账栅栏。
已有历史订单和备份恢复门禁继续适用；完整自动对账尚未实现。

## 验证范围

针对性测试：磁盘同步被阻塞时仍可查询受理结果和占用、同步模式仍等待同步、
后台失败关闭门禁、显式刷盘/检查点保存经济事实、异常空库重启及对账栅栏不自动解除、
真实子进程终止后的完整持久前缀和新 epoch。
本地 FIX 测试覆盖实际节点 ACK、同进程幂等、执行端接受、刷盘水位和异常重启。
固定 250 笔本地事务比较只测账本提交路径，不代表完整 OMS、网络或实盘吞吐量。
